# Native OS Integration Seams — Research for Wayfinder #3

> Question (issue #3): *Which Windows crate APIs and system surfaces can implement current island window geometry, topmost/click-through behavior, desktop capture, notifications, hotkeys, media/lyrics, settings, and persistence without Electron/WebView/Tauri?*

This document surfaces decision-relevant facts. It does **not** prescribe a final architecture. Where a choice exists, options are compared and constraints are called out.

Vocabulary follows `GLOSSARY.md` (Island Content, Island Behavior, Pill, Expanded Mode, Native Content Parity). ADR-0001 (full native replacement), ADR-0002 (content/behavior parity, not pixel parity), and ADR-0003 (user-supplied HLSL) are treated as fixed boundaries.

---

## 1. Method and scope

- **Source of truth for "current behavior":** the Electron main process under `D:/Project/Aeolia/dynamic-island/src/main/` **and** the Tauri v2 Rust backend under `src-tauri/src/`. The Tauri backend is unusually valuable because it already calls the exact Win32/WinRT APIs a native port would need, so it functions as a working call-pattern reference rather than a guess.
- **Primary sources for API facts:** official Microsoft Learn documentation, linked inline. Secondary sources were used only to locate the right primary page and are not cited as evidence.
- **Out of scope here:** D3D11/HLSL/Direct2D/DirectWrite/egui ownership and glass-material composition (see the parallel composition research). DWM extended-frame and layered-window surfaces are mentioned only where they affect window behavior. Video encoding remains the separate NO-GO noted in issue #1.

### Crate landscape (important framing)

## 3. Detailed findings and hard constraints

### 3.1 DPI is the dominant geometry constraint

The current logic already treats **logical pixels as the source of truth** and converts once at the boundary (`src-tauri/src/geometry.rs:141-151`), including the 125%/150% cases. Under Per-Monitor V2, Windows will not bitmap-stretch the window; the app must handle `WM_DPICHANGED` itself, using the suggested rectangle, and must recompute any cached DPI/font/size values. Microsoft explicitly warns that DPI "no longer holds true for the lifetime of a process" in multi-monitor/docking scenarios and that "it is not possible to have different HWNDs in an HWND tree run in different DPI awareness modes." ([High DPI](https://learn.microsoft.com/en-us/windows/win32/hidpi/high-dpi-desktop-application-development-on-windows))

**Decision-relevant:** any native design must pick one DPI awareness model process-wide and route all geometry through it; a "just use physical pixels" shortcut breaks parity at 125%/150% and when moving between monitors.

### 3.2 Multi-monitor means signed coordinates

The virtual screen is the bounding rectangle of all monitors; `SM_XVIRTUALSCREEN`/`SM_YVIRTUALSCREEN` are *coordinates* and can be negative when a monitor sits left of or above the primary. The current code already handles a `(-1920, 0, 1920, 1080)` monitor (`geometry.rs:312-316`) and clamps area picks to the virtual screen (`area.rs:44-57,278-284`). Also note `GetSystemMetrics(SM_CMONITORS)` counts visible monitors only, whereas `EnumDisplayMonitors` includes invisible pseudo-monitors. ([GetSystemMetrics](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-getsystemmetrics), [EnumDisplayMonitors](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-enumdisplaymonitors))

### 3.3 Protected content and capture fidelity

The three capture routes have materially different contracts:

- **GDI (`BitBlt`/`GetDIBits`)** — already implemented and proven in the repo. It reads the composed desktop DC. Hardware-overlay/DRM-protected surfaces are a known blind spot for GDI copies (they appear black); this is a platform behavior to validate empirically rather than assume away. `BitBlt` clips only to the destination DC and returns an error for an off-screen source rect. ([BitBlt](https://learn.microsoft.com/en-us/windows/win32/api/wingdi/nf-wingdi-bitblt))
- **Windows.Graphics.Capture** — official API for display/window frames; requires the system consent picker and draws a yellow border around captured items. Pixels come as D3D11 surfaces (`DXGI_FORMAT_B8G8R8A8_UNORM` in SDR; HDR pipelines need a 16-bit float format). ([Screen capture](https://learn.microsoft.com/en-us/windows/apps/develop/media-authoring-processing/screen-capture))
- **DXGI Desktop Duplication** — per-output GPU frames with dirty/move metadata; rotation and cursor must be composited by the app; all existing duplication interfaces are invalidated on desktop switch/mode change, and `DuplicateOutput` fails "if the application does not have the appropriate privilege to the new desktop image" (e.g. a secure desktop). ([IDXGIOutputDuplication](https://learn.microsoft.com/en-us/windows/win32/api/dxgi1_2/nn-dxgi1_2-idxgioutputduplication), [Desktop Duplication API](https://learn.microsoft.com/en-us/windows/win32/direct3ddxgi/desktop-dup-api))

**Decision-relevant:** the "full-screen / area / window / record" capture behaviors must be evaluated against all three, not assumed equivalent. Video recording remains a separate NO-GO per issue #1.

### 3.4 Notification permissions and identity

Two distinct problems are often conflated:

1. **Sending a toast.** Raw WinRT `CreateToastNotifier` needs package identity; the repo probes this with `GetCurrentPackageId` and falls back to an in-app banner for NSIS builds (`toast.rs:37-52,80-110`). Windows App SDK's `AppNotificationManager.Register()` sets up COM registration for unpackaged apps, which removes that blocker *if* a Windows App SDK dependency is acceptable. **Elevated apps cannot send or receive app notifications** — a hard stop independent of identity. ([App notifications overview](https://learn.microsoft.com/en-us/windows/apps/develop/notifications/app-notifications/), [Console app notifications](https://learn.microsoft.com/en-us/windows/apps/develop/notifications/app-notifications/app-notifications-console))
2. **Reading other apps' notifications.** The current implementation polls an internal SQLite database (`wpndatabase.db`) read-only. The supported alternative is `UserNotificationListener`, which requires a **User Notification Listener capability** declared in the manifest, an explicit `RequestAccessAsync()` grant from the user, ongoing `GetAccessStatus()` checks because consent can be revoked (calls then silently fail / return empty), and it is unavailable to elevated apps. It exposes app display info, creation time, ID, and the toast visual text. ([Notification listener](https://learn.microsoft.com/en-us/windows/apps/develop/notifications/app-notifications/notification-listener))

**Decision-relevant:** "no package identity" is not a fatality for toasts (Windows App SDK path exists), but it *is* a fatality for the supported notification-listener capability, which is manifest-driven. This is the sharpest packaging trade-off in the whole migration.

### 3.5 Keyboard hooks and hotkeys

The current single global accelerator (`Ctrl+Shift+S`, configurable/`off`) maps cleanly to `RegisterHotKey`, which posts `WM_HOTKEY` to a window or thread and therefore **requires a message loop** to be serviced. Documented failure modes: combo already registered by another app, window owned by a different thread, `MOD_WIN` combos reserved by the OS, F12 reserved for debuggers; `MOD_NOREPEAT` suppresses auto-repeat. ([RegisterHotKey](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-registerhotkey))

Low-level hooks (`WH_KEYBOARD_LL`) are global-only, callbacks are delivered on the installer's thread, global hooks need a DLL and matching bitness (32-bit ↔ 32-bit, 64-bit ↔ 64-bit), and UIPI blocks lower-integrity processes from hooking higher-integrity ones. ([SetWindowsHookExW](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-setwindowshookexw), [UIPI](https://learn.microsoft.com/en-us/archive/blogs/ie/protected-mode-in-vista-ie7))

**Decision-relevant:** prefer `RegisterHotKey` for a fixed accelerator; reserve hooks only if key-sequence detection is actually required. Synthesized media keys use `keybd_event`/`SendInput` (`system.rs:303-364`) and are likewise subject to UIPI when the target is elevated.

### 3.6 Click-through subtlety

Microsoft documents `WS_EX_TRANSPARENT` under *Extended Window Styles* as a paint-order style, while the mouse pass-through behavior is documented under *Layered Windows*: "if the layered window has the `WS_EX_TRANSPARENT` extended window style, the shape of the layered window will be ignored and the mouse events will be passed to other windows underneath." Separately, color-keyed or alpha-zero regions of a layered window pass mouse messages through even without the style. The current implementation toggles `WS_EX_TRANSPARENT` on a WebView-backed window; a native port should verify the style change actually takes effect (Microsoft documents that after `SetWindowLong`, a `SetWindowPos(..., SWP_FRAMECHANGED)` call is needed for style changes to apply) and consider `WM_NCHITTEST`→`HTTRANSPARENT` for region-level control. ([Window Features](https://learn.microsoft.com/en-us/windows/win32/winmsg/window-features), [Extended Window Styles](https://learn.microsoft.com/en-us/windows/win32/winmsg/extended-window-styles), [SetWindowPos](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-setwindowpos))

## 4. Unresolved decisions this research does **not** make

1. **Packaging:** packaged/MSIX vs unpackaged/NSIS vs Windows App SDK bootstrapper. This determines raw WinRT toasts, the notification-listener capability, and `ApplicationData` availability. It is the single most consequential open decision for OS seams.
2. **Capture backend:** GDI (already proven in-repo) vs Windows.Graphics.Capture (consent UI + yellow border) vs Desktop Duplication (per-output + D3D11). Choice depends on whether window/area capture and future video are in scope.
3. **Notification reading:** continue the read-only toast-DB poll (fragile but identity-free) or adopt `UserNotificationListener` (supported, but capability + consent + packaging constraints).
4. **Hotkey mechanism:** `RegisterHotKey` vs low-level hook. Fixed accelerator → former; arbitrary key sequences → latter with its DLL/bitness/UIPI costs.
5. **Persistence medium:** keep `%APPDATA%` JSON (best fidelity for existing state/settings files, zero OS-API coupling) vs `ApplicationData` vs registry. ADR-0002 favors preserving current files.
6. **Elevation policy:** running elevated breaks app notifications entirely; if any Island Behavior requires elevation, that must be resolved explicitly.
7. **DPI awareness model:** Per-Monitor V2 is the documented modern target, but it shifts full layout responsibility onto the app and must be chosen process-wide.
